Per key keyboard lighting, lighting that survives a suspend, and a colour wheel
that selects the colour you clicked.

## Why

The keyboard controller was mapped and wired up, but three things made the
result wrong in daily use. Lighting never came back after the laptop slept. The
colour wheel was mirrored, so clicking a colour selected its reflection. And the
key index table had been inferred from the visual layout rather than measured,
which mislit thirteen keys.

## Keyboard map corrected

The four media keys are NOT spliced into the middle of the number row. They sit
below it, at 16 to 19, and the number row is contiguous from 20 to 32.

| indices | keys |
| --- | --- |
| 16-19 | volmute, voldown, volup, micmute |
| 20-32 | grave, 1 through 0, minus, equals |
| 81 | left shift, was wrongly 78 |

The old table only looked right at 8, 9, 0, minus and equals, because the
invented gap closed up again by index 28. The test suite passed green the whole
time because it asserted the same wrong values the code used.

## Changed

- Lighting and the thermal profile are re-applied on resume. The plugin watches
  logind PrepareForSleep and re-arms its restore latches, which previously
  latched once and never fired again for the life of the shell
- Restoring keyboard lighting never raises a password prompt. The polkit check
  for `set-keyboard` is non interactive, so a locked session declines quietly
  and the retry ladder applies the colours after unlock
- The two mute keys follow PipeWire, red while muted, as an overlay that is
  never written into the saved colours
- The theme colour paints the keyboard, not only the chassis
- The colour wheel is no longer mirrored, the hit area matches the painted disc,
  and dragging no longer round trips through an 8 bit hex that destroyed hue
- `kbd identify <idx>` lights one key and blanks the rest, so the index map can
  be verified without hand written scripts
- hidraw opens take an advisory flock, so the CLI, the daemon and the plugin
  serialise on the same node instead of racing and wedging the controller
- The daemon keeps the keyboard device open instead of reopening it per call
- `rgb status` no longer runs while a write is queued
- elc readiness is a real reading rather than a hardcoded true
