Lighting now speaks the AlienFX protocol directly. OpenRGB is gone.

## Why

OpenRGB reads this laptop's platform id as 0x306, which is absent from its
tables, so it fell back to sequential hardware zone ids 0 to 19 and named every
zone "Unknown". The real layout is sparse and spans 0 to 23. Nearly every write
addressed ids that do not exist on this hardware, which is why only the power
button ever responded and why the lid logo and the chassis ring could never be
lit at all.

## Changed

- Lighting speaks AlienFX APIv4 straight to `/dev/hidraw0`. No server, no
  socket, no network surface
- Four named regions replace twenty anonymous slots

| Region id | Name | LEDs | Hardware zone ids |
| --- | --- | --- | --- |
| `power` | Power button | 1 | 0 |
| `logo` | Lid logo | 1 | 1 |
| `ring-top` | Ring top | 8 | 8-15 |
| `ring-bottom` | Ring bottom | 8 | 16-23 |

- `rgb set-map` writes several regions in one device transaction and leaves
  regions it does not name untouched
- The RGB tab is rebuilt around multi select. Pick any combination of regions
  and assign one colour
- A colour picker with theme swatches and hue, saturation and value sliders
- The package ships its own udev rule. Removing OpenRGB no longer takes HID
  access with it

## Fixed

- The write queue keyed only on the verb, so a colour write to one zone evicted
  a queued write to another. Assigning colours to several regions was impossible
- The colour field fell through to colouring the whole machine when the cursor
  was not on a valid target
- Theme sync never fired. The theme colour is now bound to the live shell accent
- Asking for 100 percent brightness wrote 0, because the device reports a
  degenerate range and the value was passed through unchecked
- Identify no longer leaves the device in a different lighting mode
- The first run wizard could ambush a user who had named and then hidden zones

## Removed

- The OpenRGB backend, its systemd unit and its optional dependency
- The zone naming wizard, zone renaming and the persisted zone map. Regions are
  fixed and known, so none of it has a purpose

## Not implemented

- Lighting effects. `rgb mode` is recognised and answers `not-supported`
- Keyboard lighting. The keyboard is a separate Darfon controller on a root only
  HID node and needs the daemon plus a polkit action
